## 2024-11-08 - Fix Open Redirect Vulnerability Bypass

**Vulnerability:** The application's redirect validation logic `getSafeRedirectUrl` used naive string prefix checks (`startsWith("/")` and `!startsWith("//")`) to validate relative redirects. However, by inserting control characters like tabs (`\t`) or newlines (`\n`) after the first slash (e.g., `/\t/evil.com`), attackers could bypass the string prefix checks while the underlying `URL` constructor strips the control characters and processes it as an absolute URL (or protocol-relative URL) directed to `evil.com`. This allowed an Open Redirect vulnerability (CWE-601).
**Learning:** String prefix validation is insufficient when dealing with parser inconsistencies. The JavaScript `URL` constructor normalizes malformed inputs in ways that circumvent simple string pattern matching. Validating the state of the *parsed* object (e.g., verifying `parsed.hostname === "localhost"`) rather than just the *unparsed* string is necessary for robust URL security.
**Prevention:** Always validate URLs post-parsing. When using a dummy domain (like `http://localhost`) to parse supposedly relative paths, assert that the parser did not interpret the input as an absolute URL by ensuring the hostname remains the dummy domain.
